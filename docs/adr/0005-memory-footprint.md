# ADR-0005 记忆库存储占用：压实为主，清洗为辅，裁边默认关闭

状态：已采纳（0.13.3）

## 背景

面板里记忆库显示 9.21 MB，而 wiki 只有 60 个页面、记忆条目 222 条。用户最初的判断是「分片正文里塞了太多表格竖线（`|`）等格式字符」。

实测把这个前提否掉了：

| 成分 | 字节 | 占 9.65 MB |
|---|---|---|
| 空闲页（`freelist_count` 560 × 4096） | 2,293,760 | **24%** |
| `edges` 的六个索引 | ~3,028,000 | **31%** |
| 活条目正文 `SUM(LENGTH(content))` | 235,541 | **2.4%** |
| 活条目向量（222 × 4096） | 905,216 | 9.4% |
| 软删条目向量（325 × 4096） | 491,520 | 5.1% |
| `oplog.detail` | 346,353 | 3.6% |

222 条活记忆的正文里，竖线一共 **846 个**，只占正文的 0.63‰。换句话说：把全文所有竖线、星号、反引号全删光，省下的空间在 9.65 MB 里连 0.1% 都不到。

真正撑大文件的是三件事：`forget` 只写 `deleted_at` 不真删（325 条软删行连向量一起留着）、SQLite 从不回收空闲页、以及每条记忆平均带 21 条 `edges` 而 `edges` 上有六个索引。

## 决策

分三层，按收益排序：

### 1）压实（默认开启，收益 51%）

新增 `--compact` 子命令：

1. `DELETE FROM insights WHERE deleted_at IS NOT NULL`
2. `DELETE FROM edges WHERE source_id NOT IN (SELECT id FROM insights) OR target_id NOT IN (SELECT id FROM insights)`
3. `mnemon gc --compact`（官方 VACUUM 入口；直接发 `VACUUM` 在 WAL 模式下会失败）

实测副本库 `9,654,272 → 4,677,632` 字节（**−51.5%**），活条目 222 条一条没少，`PRAGMA integrity_check` = ok。

`--compact` **不进 `--all`**，避免每日全量管线无条件改写 9 MB 的库。改为在 `--sync` 结束后跑一次 `shouldAutoCompact()`：空闲页占比 ≥ 15% 或软删 ≥ 200 条才动手；`LLM_WIKI_COMPACT_AUTO=0` 可关。

### 2）正文清洗（默认开启，收益微小但可读性明显）

`cleanChunkText()` 在切块时处理：

- 代码围栏（` ``` ` / `~~~`）内的内容一律不动
- 表格分隔行（`|---|`）整行删掉
- **以竖线开头的行**把 `| a | b |` 转成 `a · b`（只判断行首，因为 `splitLong` 会在 `CHUNK_MAX` 处截断，行尾未必闭合）
- 连续空行折叠成两个
- `（来源: …）` 回流锚点不碰

实测在真实 222 条活记忆上：字符 `134,890 → 133,819`（−0.79%），竖线 `846 → 124`（−85%），改动 32 条。**省不出空间，但检索命中的片段不再是表格骨架。**

### 3）裁边（默认关闭，有损）

`LLM_WIKI_COMPACT_PRUNE_EDGES=1` 才执行，做法是删掉 `edge_type='entity' AND source_id IN (SELECT id FROM insights WHERE importance < 4)`。

收益不小：再省 1.66 MB（累计 −69%），`edges` 4,708 → 1,414。但召回有实际损失，见下。

## 被否的方案

### 否：把正文里的 markdown 全剥掉

竖线只占 0.09%，剥掉全部格式符号也省不到 0.5%。而 `##`、列表、代码块是 wiki 页面的结构，剥掉会让分片失去可读性，也让 BM25 丢掉结构性线索。

### 否：只给 `importance >= 3` 的条目建向量

向量共占 14.5%，砍一半也就 7%。但向量是向量召回的唯一样本，删了没法补（要重跑 embed 且 hash 未变的页面不会被重导）。收益与代价倒挂。

### 否：改 mnemon 本体做量化 / 半精度向量

1024 维 float32 是 mnemon 的存储契约，改本体意味着 fork 一个第三方二进制，升级即失效。

### 否：靠 `entities` 字段控制 entity 边

实测发现 `entities` 不控制边：传 `entities: []` 与传 `entities: ["dsh-llm-wiki"]` 导入后**都新增 10 条边**，mnemon 用自己抽的实体覆盖传入值。所以「只给高 importance 建 entity 边」在管线侧做不到，只能在 `--compact` 里按 SQL 事后裁——这也是它必须有损且默认关闭的原因。

## 重新评估「裁边」的触发条件

裁边方案之所以默认关闭，是因为 A/B 实测：

- **同库同查询连跑两次结果就不同**：10 个查询 × 5 次，top-3 完全一致的只有 44%。单次召回结果不能作为判据。
- 用 5 次 top-10 并集算「可召回集合」：`purged`（只清软删不裁边）平均 Jaccard **0.577**，`trimmed`（裁边）**0.516**，集合大小 15.2 → 14.1 / 13.3。

即：清软删几乎无损（−7%），裁边额外掉 13%。抽样的 `importance<4` 条目（如局域网入站不通、手工记账真机联调）恰恰是靠 entity 边被召回的。

若将来 `edges` 增长到成为主要矛盾（比如单库超 100 MB），再谈裁边，并应先把 `entity` 边的抽取规则改到源头。

## 后果

- 面板「存储占用」卡片显示库大小、空闲页占比、待清理条目数，并给「压实记忆库」按钮（`POST /api/run {command:"compact"}`）。空闲页 < 5% 且无软删时按钮置灰显示「无需压实」。
- 手动入口：`node scripts/llm-wiki-pipeline.mjs --compact`。
- 清软删是**不可逆**的：被 `forget` 掉的条目内容与向量都会消失。这符合 `forget` 的语义（用户主动忘掉），但意味着压实前不能靠改 `deleted_at` 反悔。
